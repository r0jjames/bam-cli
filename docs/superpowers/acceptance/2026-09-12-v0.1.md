## Step 3 — what failed, and the fixes

1. **`bam build cancel` never worked on Data Center 12** (item 10). `DELETE /rest/api/latest/queue/{buildKey}` answers 404 `Plan LAB-PROV is not of type …ImmutableJob`: the endpoint takes a **job** result key. `StopBuild` now falls back to deleting every unfinished job of the build, and reports not found only if no job could be stopped. Regression tests: `TestStopBuildFallsBackToJobKeys`, `TestStopBuildWithNoStoppableJobReportsNotFound`.
2. **A stopped build showed as "not built"** (item 10). Bamboo settles it as `lifeCycleState: NotBuilt`, `state: Unknown` — the shape of a job that never ran. `stateOf` maps it to `stopped` when the build has a start time and `notRunYet` is false. Tests: `TestStoppedBuildMapsToStopped`, `TestNeverStartedBuildStaysNotBuilt`.
3. **An unknown subcommand of a group command exited 0** (found while cleaning up item 14): `bam server remove alt` printed help and exited 0, so a typo looked like success. `requireSubcommand` gives every group command a `RunE`: bare it prints help, an unknown subcommand is a usage error (exit 2), like `bam nosuchcmd`. Tests: `TestUnknownSubcommandIsUsageError`, `TestGroupCommandWithoutArgsPrintsHelp`.

Bamboo behaviour worth knowing, documented in `bam build cancel --help` and spec §9: a stop removes the build's unfinished jobs from the queue, so a stage that had not started yet can still be queued afterwards. Observed once (`LAB-PROV-7` ran its second stage to a failure after the cancel); a cancel during the running stage stops the build (`LAB-PROV-9`).

Caveats carried forward, not defects: `failed tests` is unsupported on this server (item 2), and branch-plan URLs were not exercised because the lab plan has no branches (item 12).

## Step 4 — final review from three perspectives

**Product.** The loop the PRD set out to remove — open Bamboo, find the plan, retype variables, click, watch, dig for the failing job — is gone for a single run: `bam run provision-lab --var cluster_config=lab1 --watch` then `bam logs --last --failed` produced the failure cause in two commands, and `--from last` re-runs with the previous values. Variable validation catches a wrong value before a build is queued (item 6), which is the click-ops failure the PRD calls out. Parallel run sets remain out of scope for v0.1.

**Developer.** `bam --help` groups commands as Setup / Browse / Run / Shortcuts, and every failure ends with a `try:` line pointing at the next command (`bam logs … --failed`, `bam open …`, `bam login alt`). The shortcuts (`run`, `watch`, `logs`, `url`, `open`) mean the common path never needs the noun. Setup is three commands (`server add`, `login`, `init`) and nothing needs an environment variable — the developer tools read the same config (`make record ARGS='-target provision-lab'`).

**Senior engineer.** `go list -deps` confirms the layering: `app` pulls only `errs`, `config`, `provider`; cobra appears in `cli` alone; `provider/bamboo` is imported by `cli` only; the new `toolcfg` sits on `config`, `credential`, `errs`. `TestAppStaysUIReady` passes. Files over 400 lines: `tools/record/main.go` (658 — fetching, scrubbing and denylist upkeep in one tool; the scrub helpers are the natural split when it grows again), `internal/cli/runloop.go` (477) and `internal/cli/browse.go` (427), both of which are command definitions of one group each. `view` imports `config` as well as the table says — it renders target and server names — worth a line in the architecture table rather than a change.
