# bam v0.3: `bam run --edit`

**Status:** Implemented | **Date:** 2026-09-22
**Product requirements:** [`docs/prd.md`](../../prd.md) "Then (v0.3)"
**Builds on:** [`2026-09-12-bam-cli-mvp-design.md`](2026-09-12-bam-cli-mvp-design.md) §2.3 (variable resolution), §3.6-3.7 (secrets, `${ENV}` references), §7 (JSON contract)

All hosts, keys and user names are placeholders.

## 1. Problem

`bam run` resolves variables from four sources (plan < target `defaults` < `--from` < `--var`), prints the result and triggers. To change one value the user has to retype it as `--var name=value`, and to see what a run would send before changing anything they need a separate `--dry-run`. A preset with a `required` name and no value cannot be run at all without knowing the name in advance.

`bam run --edit` opens the resolved variables in the user's editor, re-validates what comes back, and then continues exactly as `bam run` does: print, trigger, and optionally watch.

## 2. Command

```
bam run <plan|target> --edit [--var k=v]... [--from N|last] [--branch B]
        [--watch] [--timeout D] [--dry-run] [--json]
```

`--edit` is a flag on `bam build run` and therefore on its `bam run` shortcut. It combines with every existing flag.

- `--dry-run`: edit, validate, print the resolved set, trigger nothing, exit 0.
- `--watch` (or a target with `watch: true`): after the trigger, watch as today.
- `--json`: the document of MVP spec §7 is written after the editor closes, unchanged in shape (section 8). Section 7 covers the terminal requirement.

Precedence becomes: plan < target `defaults` < `--from` < `--var` < **edit**.

## 3. Flow

1. **Terminal check.** stdin and stdout must both be terminals (`Env.StdinTTY`, `Env.StdoutTTY`). Otherwise: usage error, exit 2, `--edit needs a terminal`, Try `pass the values with --var`. The check runs before any configuration load or network call. It applies with `--json` too.
2. **Fetch.** `ResolvePlan`, then `svc.VarBase(ctx, ref, from)`. Errors here stop the command as they do today: unknown target, auth, network, a `--from` build that cannot be read.
3. **Apply flags.** `app.ApplyVars(ref, base, flags)` gives the set the buffer opens with (the *opened set*). It fails only on `--var` syntax. Then `app.ValidateEdited(ref, base, flags, nil, getenv)` is called for its error only. A rule error (unset `${ENV}`, `required`, `options`) does **not** stop the command. It goes into the first buffer's error block (section 4.3).
4. **Edit loop.**
   1. Render: `app.EditBuffer(ref, opened, getenv, server, dryRun, errors)` on the first round. On later rounds: `app.ReopenBuffer(userText, errors)`.
   2. `Env.RunEditor(cmd, buffer)`. A non-zero editor exit aborts.
   3. `app.ParseEdits(text, ref, opened)`. A buffer without variable lines aborts. Parse problems: back to step 1 with the user's text.
   4. `app.ValidateEdited(ref, base, flags, edits, getenv)`. A rule error: back to step 1 with the user's text.
   5. Otherwise the loop ends with the validated `VarSet`.
5. **Continue as `bam run`.** Print warnings, then `view.RunPlan` (or the JSON document). Then `--dry-run` stops, or `svc.Run` triggers, and `--watch` watches.

**Abort** (empty buffer, or the editor exits non-zero, for example `:cq` in vim): stderr `run aborted: nothing triggered`, exit 130, nothing triggered. 130 is the same code as an interrupt: both are a user cancel.

The loop has no retry limit; the user leaves it by fixing the buffer or by aborting.

## 4. Buffer format

`name=value` lines, the same shape as `--var`.

```
# error: environment="qa" is not allowed by target provision-lab
#   allowed: dev, staging, prod
# error: line 14: name "cluster name" may use only letters, digits, _ . -
#
# bam run provision-lab · PROJ-PROV · branch main · server lab
# One variable per line, name=value. Save and quit to run.
# ******** keeps a secret's current value. A value of exactly ${NAME} reads the environment.
# Delete a line to keep its value. Delete every line, or quit with an error (:cq), to abort.

# plan
app_version=1.4.2
# flag (plan: "beta")
cluster_name=alpha
# target, ${DB_PASSWORD} unset, secret
db_password=********
# target, required, options: dev|staging|prod
environment=staging
# required
release_ticket=
```

### 4.1 Rendering

- **Names.** Every variable of the opened set (plan, target `defaults`, `--from`, `--var`), plus each target `required` or `options` name not yet in the set, with an empty value. This is the same rule as the terminal UI's run form (`buildFields`). Sorted by name.
- **Header.** Target name or plan key, the plan key, the branch (`default branch` when `ref.Branch` is empty) and the server alias, then the four instruction lines above. With `--dry-run`, "Save and quit to run" reads "Save and quit to preview".
- **Per-variable comment,** always on its own line above the variable, never at the end of the line, because `#` may be part of a value. The parts, in this order, comma-separated:
  - the source (`plan`, `target`, `from #N`, `flag`), omitted for a name added only because it is `required` or has `options`
  - `${NAME} set` or `${NAME} unset`, for a target default that is an environment reference
  - `required`
  - `options: a|b|c`
  - `secret`
  - ` (plan: "X")` appended to the source, when the variable is declared, not a secret, not from the plan, and its value differs from the plan value

  A row with no parts (impossible today) gets no comment line.
- **Secrets.** A secret variable (MVP spec §3.6 name pattern, masked by Bamboo, or a `${ENV}` target default) with a non-empty value shows `********`. A secret with an empty value shows empty, which reveals nothing. The buffer never holds a real secret value, including in comments and error lines.
- **Values that cannot round-trip.** A non-secret value containing `\n` or `\r`, or a name that does not match `^[A-Za-z0-9_.-]+$` (never produced by `--var` or the plan, but never proven impossible either), gets no `name=value` line at all, only its comment with `, multi-line value, kept as is` or `, name cannot be edited here, kept as is` appended; no line means `ParseEdits` keeps the resolved value, so a save-unchanged round trip cannot truncate the value or inject a bogus variable from what follows the first newline.

### 4.2 Parsing

- Blank lines are ignored. A line whose first non-space character is `#` is ignored.
- Any other line is split on the first `=`. The name is trimmed of surrounding spaces and must match `^[A-Za-z0-9_.-]+$`. The value is everything after the `=`, verbatim, as with `--var`. The only exception is a trailing `\r`, which is stripped.
- Problems, all collected with their line numbers rather than stopping at the first. A problem names the line number and at most the name, never the value or the raw line, because the line may hold a typed secret:
  - a line without `=`: `line N is not name=value`
  - a name that does not match the pattern: `line N: name "x y" may use only letters, digits, _ . -`
  - a name that appears twice: `line N: x is also on line M` (a file is not a flag list; a duplicate is a mistake, not last-wins)
  - the value `********` for a name that was not a secret in the rendered rows: `line N: x: ******** is the mask; type the real value`. This stops asterisks from overwriting a real value.
- A buffer with no variable lines means abort.

### 4.3 Errors in the buffer

The error block sits at the top, one `# error: ` line per problem, followed by a `#` line. It holds every parse problem, then the first rule error from `ValidateEdited` run on the edits of the lines that did parse (it stops at its first error, as `ValidateVars` does today). A rule error shows its `What`, and its `Why` on an indented `#   ` line below it; its `Try` is dropped, since it suggests `--var`.

`ReopenBuffer` removes the leading error block of the user's text (leading `# error: ` lines, their `#   ` continuation lines, and the single `#` line after them) before adding the new one, so blocks never stack. `EditBuffer` is `ReopenBuffer` applied to the fresh rendering. It changes nothing else: the user's edits, including a secret they typed, stay as they left them for the next round.

### 4.4 What counts as an edit

Each variable line is compared with the **rendered rows**: the opened set plus the empty `required` and `options` names of section 4.1. It is never compared with the text of an earlier round. `ParseEdits` rebuilds the rows from `ref` and the opened set, so it needs no state from the first render.


| Line | Edit? |
| --- | --- |
| secret still `********` | no; the resolved value stands |
| value equal to the rendered value | no |
| value different, including empty | yes |
| name not in the rendered rows | yes |
| line deleted | no; the resolved value stands |

Only edits reach `ValidateEdited`. A buffer saved unchanged therefore gives exactly the result `ResolveVars` would give, with no extra warnings.

### 4.5 Temp file

`os.CreateTemp("", "bam-run-*.env")`, mode 0600. The `.env` suffix gets syntax highlighting in most editors. The file is deleted after every round, on success, error and abort, so a secret the user types sits on disk only while the editor is open.

## 5. Variable rules for edits

- An edited value becomes source `edit`.
- An edited value that is exactly `${NAME}`, with `NAME` matching `^[A-Za-z_][A-Za-z0-9_]*$`, is read from the environment, as a target default is (MVP spec §3.7). It becomes source `env` and secret. An unset one is the same usage error as for a target default, shown in the buffer.
- An edited name that the plan does not declare and the target does not list gets the same warning and did-you-mean as an undeclared `--var`. It is printed on stderr after the editor closes. The warning is not repeated for a name already warned about as a `--var`.
- `required` and `options` apply to the final set as today.
- Only variables whose value differs from the plan's are sent (`VarSet.Changed`).

## 6. Architecture

The layering of CLAUDE.md is unchanged. No package gains an import.

### 6.1 `app`

New file `internal/app/edit.go`:

```go
// Edit is one variable changed in the editor.
type Edit struct{ Name, Value string }

func ApplyVars(ref PlanRef, base VarSet, flags []string) (VarSet, error)
func ValidateEdited(ref PlanRef, base VarSet, flags []string, edits []Edit,
    getenv func(string) string) (VarSet, error)

func EditBuffer(ref PlanRef, opened VarSet, getenv func(string) string,
    server string, dryRun bool, errors []string) []byte
func ReopenBuffer(text []byte, errors []string) []byte
func ParseEdits(text []byte, ref PlanRef, opened VarSet) (edits []Edit, abort bool, problems []string)
```

`ValidateVars` keeps its signature (the terminal UI calls it) and becomes `ValidateEdited(ref, base, flags, nil, getenv)`. Internally the function is split into three steps: apply flags then edits, resolve `${ENV}` for sources `target` and `edit`, check the rules. `ApplyVars` is the first step on its own. The existing `vars_test.go` cases pin the behaviour of `ValidateVars` and `ResolveVars`.

The buffer codec lives in `app`, not `view`, because rendering and parsing are one round-trip contract. The `********` sentinel, the edit diff and the reopen block must agree, and `view/tui` may reuse the pair later. The functions return bytes and never write to a stream or read stdin, so `TestAppStaysUIReady` holds.

`PlanRef` carries no server, so `EditBuffer` takes the server alias as a parameter; `PlanRef` is not widened.

### 6.2 `config`

The machine file schema gains `editor` (string, optional), next to `pager`.

### 6.3 `view`

- `EditorCommand(getenv, machineEditor, goos string) string` next to `PagerCommand`: `BAM_EDITOR`, then machine `editor`, then `VISUAL`, then `EDITOR`, then `vi`, or `notepad` on Windows.
- `RunPlan` shows source `edit` like every other source label.

### 6.4 `cli`

- `Env.RunEditor func(cmd string, initial []byte) ([]byte, error)`, defaulting to `runEditor` in a new `internal/cli/editor.go`, modelled on `pager.go`. `runEditor` writes `initial` to the temp file of section 4.5, splits `cmd` on whitespace (so `code --wait` works), appends the file path, runs it with the process's stdin, stdout and stderr, reads the file back and deletes it in a `defer`.
  - A non-zero exit returns `errEditorCancelled`.
  - A command that cannot be found is a config error (exit 3): ``editor `vi` not found``, Try `set BAM_EDITOR or EDITOR`.
- New file `internal/cli/runedit.go`: `(r *runtime) editVars(ctx, ref, base, flags, dryRun) (app.VarSet, error)` runs the loop of section 3.
- `newRunCmd` gains `--edit` ("review and change the variables in $EDITOR before running"). With `--edit` it calls `VarBase` and `editVars` in place of `ResolveVars`. Everything after the resolved set is unchanged.
- Abort prints `run aborted: nothing triggered` on stderr and returns `silentError{context.Canceled}`. That path already exists: `runtime.wrap` passes a `silentError` through, `Execute` prints nothing more for it, and `exitCode` maps `context.Canceled` to 130. No new error type.
- If ctx is cancelled while the editor is open (Ctrl-C), the command exits 130 once the editor returns, as an interrupt does today.

## 7. Errors and exit codes

| Case | Checked | Result |
| --- | --- | --- |
| stdin or stdout not a terminal | first | usage, exit 2 |
| bad `--var` syntax, unknown target, auth, network, unreadable `--from` | before the editor | as today: 2, 3, 4 or 5 |
| unset `${ENV}`, `required`, `options` | before and after the editor | error block, editor reopens |
| parse problems | after the editor | error block, editor reopens |
| no variable lines, or editor exits non-zero | after the editor | `run aborted: nothing triggered`, exit 130 |
| editor command not found | first launch | config, exit 3 |
| interrupt while the editor is open | editor returns | exit 130, nothing triggered |
| trigger or watch errors | after the editor | as today |

A secret's value never appears in the buffer, in an error line, in a warning, in `RunPlan` output, in JSON or in `--debug` output. An `options` error on a secret already shows `********` through `ResolvedVar.Display`.

## 8. JSON

No change. The `build run` document's `variables` is a name-to-value map of the changed variables, with no source. An edited value appears there like any other changed value, masked when secret. The `--watch --json` NDJSON stream is unchanged.

## 9. Testing

TDD per task. No test runs a real editor, sleeps or reaches the network.

- **`app/edit_test.go`**, table-driven:
  - rendering: header, `--dry-run` wording, comment parts, secrets as `********`, `required` and `options` names added, `(plan: X)`

  - render then parse without changes gives no edits
- **`app/vars_test.go`**:

- **`cli/runedit_test.go`**, through the harness, with a scripted `RunEditor` that returns buffer N on call N and records every buffer it receives:

## 11. Acceptance

- `bam run provision-lab --edit` opens the editor on the resolved set. Saving unchanged triggers exactly what `bam run provision-lab` would trigger.
- A changed value is sent and printed with source `(edit)`. An unchanged secret keeps its resolved value, and no secret value is ever written to the buffer.
- `--dry-run`, `--watch` and `--json` behave as without `--edit` once the editor closes.
- A target with an unset `required` name opens the editor with the error shown, instead of failing.
- An invalid buffer reopens with the errors and the user's own text. An empty buffer or `:cq` exits 130 without triggering.
- Without a terminal, `--edit` exits 2 before any network call.

## 12. Out of scope

- An editor key in the terminal UI's run form. The codec in `app` is designed so it can be added later.
- Multi-line values.
- Opening `/dev/tty` so that `--edit` works with piped stdout.
- `run --revision` and `run --verbose`. They need the capability probe and fixture recordings, and get their own spec.
